# 矿业智询｜MVP 架构草案

本次仅定义方案，以下能力均待实现。沿用原生前端、Flask 和 SQLite 基础，将 MVP 扩展为四个代表性 Case。

## MVP Case 与能力映射

| Case | 用户问题示例 | 能力与输出 |
| --- | --- | --- |
| 1. 政策问答 | 储量年报什么时候提交？ | RAG + Citation：检索适用政策，返回截止时间及来源 |
| 2. 材料问答 | 储量年报需要准备什么？ | RAG + Citation：返回材料清单及来源 |
| 3. 业务状态查询 | 演示矿山 A（虚构）2026 年储量年报提交了吗？ | Tool Calling + Mock API：返回提交状态与时间 |
| 4. 综合判断 | 演示矿山 A（虚构）2026 年还没交，现在算逾期了吗？ | RAG + Tool + Rule + LLM：结合适用规则与记录，返回程序判断及依据 |

四个 Case 共用入口，按知识查询、业务查询、综合判断分支处理。原有资料齐全查询可作为业务查询的后续扩展。

## 整体系统链路

用户 → 原生网页 → Flask 后端（校验与编排）→ 按问题类型调用 RAG / Tool / Rule → LLM 组织答案 → 后端返回结果与依据 → 网页展示。

- 知识查询：检索适用政策片段 → 生成带来源的回答。
- 业务查询：提取并校验矿山、报告年度、资料类型 → 调用只读 Mock API → 返回记录。
- 综合判断：获取适用政策与提交记录 → 确认截止时间及查询时间 → 程序判断 → 生成结论与依据。

LLM 负责理解问题与表达；状态、缺项和逾期结论由数据及确定性程序给出。矿山不明确、年度缺失、规则冲突或证据不足时，应澄清或说明无法判断。查不到记录不能直接视为未提交，须确认数据覆盖完整；报告年度与提交年份应分别处理。

## 主要组件

| 组件 | 计划职责 |
| --- | --- |
| 原生 HTML / CSS / JavaScript | 提问、加载状态、答案、来源与错误提示 |
| Flask 后端 | 参数校验、流程编排、模型调用与只读工具接口 |
| SQLite + Mock API | 保存并查询明确标注的虚构矿山、应交清单及提交记录 |
| 知识库 / RAG | 检索少量选定政策或演示规则，保留来源、条款、日期与适用范围 |
| Rule | 根据已核验的截止时间、查询时间与业务记录执行确定性判断 |
| LLM | 意图识别、参数提取及基于证据的回答；供应商与模型待定 |
| Dify（待评估） | 可用于知识库与流程编排，后续确定是否接入 |

## 范围与下一步

第一版只验证上述四个 Case，不接入真实业务系统，不自动审批或修改业务数据，不作行政执法决策。虚构数据与演示规则须明确标注。

1. 选定储量年报的演示范围，整理可追溯的政策材料或演示规则，确认适用地区、年度、截止时间与材料清单。
2. 定义只读 Mock API 输入输出及虚构数据，覆盖已提交、未提交和数据缺失。
3. 确定 RAG 与编排实现方式，评估 Dify，补充配置说明。
4. 按知识问答、状态查询、综合判断顺序实现与联调，验证引用、异常提示和截止时间边界。
5. 完成四个 Case 的演示与部署说明，按阶段检查并提交。
